## Prompt

An alert shows an unusual AWS IAM access key usage from a new geography. Describe investigation and containment steps for a cloud-focused SOC team.

## Response

When an alert triggers for unusual AWS IAM access key usage from a new geography (often generated by services like Amazon GuardDuty), it is a high-priority event that suggests potential credential compromise.

Here is a step-by-step guide on how a cloud-focused SOC team should investigate and contain this threat.

**Phase 1: Investigation (Detection & Analysis)**

The goal here is to determine if this is a legitimate action (e.g., a user traveling or using a new VPN) or a true security breach, and to assess the "blast radius."

**1. Validate the Source IP and Context**

- **IP Intelligence:** Query the anomalous IP address using Threat Intelligence tools. Is it associated with Tor exit nodes, known malicious botnets, or commercial VPN providers (like NordVPN)?
- **Corporate vs. Public:** Check if the IP belongs to a newly provisioned corporate network or a legitimate remote-work ISP.
- **Impossible Travel:** Check CloudTrail to see if the same IAM key was used from its normal geographic location concurrently or within a physically impossible timeframe.

**2. Identify the Identity and Privileges**

- **Human vs. Machine:** Determine if the access key belongs to a human user or a service account (machine identity). A human might be on vacation; a service account authenticating from a new geography is almost certainly compromised.
- **Assess Permissions:** Review the IAM policies attached to the user or role. Do they have broad administrative access, or are they scoped to a specific S3 bucket? This tells you the potential blast radius.

**3. Analyze CloudTrail Logs for Malicious Activity**

Query AWS CloudTrail (via Athena, CloudWatch Logs, or your SIEM) filtering by the specific `userIdentity.accessKeyId`. Look for patterns indicating the cyber kill chain:

- **Reconnaissance:** High volumes of `Describe*`, `List*`, or `Get*` API calls (e.g., `ListBuckets`, `DescribeInstances`).
- **Privilege Escalation:** Attempts to call `CreateUser`, `AttachUserPolicy`, or `CreateAccessKey`.
- **Defense Evasion:** Attempts to disable CloudTrail, GuardDuty, or delete VPC flow logs (`StopLogging`, `DeleteDetector`).
- **Exfiltration/Impact:** API calls like `RunInstances` (crypto-mining), `DeleteBucket`, or downloading objects from sensitive S3 buckets.
- **Analyze the userAgent:** Attackers often use scripts or automation tools (e.g., Boto3, Kali Linux, Pacu cloud exploitation framework) which might be reflected in the user agent string.

**4. Out-of-Band Verification**

If the key belongs to a human, contact them via Slack, Teams, or phone (do not use email if you suspect their account is compromised) to ask if they are traveling or testing a new VPN.

**Phase 2: Containment**

If the investigation confirms or heavily suspects unauthorized access, the SOC must act immediately to stop the bleeding without destroying forensic evidence.

**1. Disable (Do Not Delete) the Access Key**

Go to the IAM console or use the CLI to mark the specific Access Key as Inactive.

Why not delete? Deleting destroys the metadata of the key. Making it inactive immediately stops its usage while preserving evidence for the post-incident review.

**2. Apply a Quarantine Policy (Explicit Deny)**

Attach an inline IAM policy to the compromised User or Role with an explicit Deny for all actions. In AWS IAM, an explicit deny overrides any allows.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Deny",
      "Action": "*",
      "Resource": "*"
    }
  ]
}
```

**3. Revoke Active Temporary Sessions (If Applicable)**

If the compromised entity is an IAM Role (accessed via STS) rather than a static IAM user, disabling an access key isn't enough, as the temporary tokens might still be valid (up to 12 hours).

Attach a policy that denies access to any session issued before the exact time of containment. AWS provides a specific action for this: RevokeSession (which automatically attaches the `aws:TokenIssueTime` condition policy to the role).

**4. Contain the Blast Radius (Resource Level)**

If CloudTrail analysis showed the attacker spun up unauthorized resources (e.g., EC2 instances in unused regions for crypto-mining), isolate them.

Change the Security Groups of rogue EC2 instances to block all inbound and outbound traffic rather than terminating them immediately, to allow for memory/disk forensics if needed.

**Phase 3: Eradication and Remediation (Next Steps)**

Once contained, the SOC hands over or executes the cleanup phase:

- **Credential Rotation:** Generate a new access key for the user/service once the environment is secured. Rotate any other secrets (database passwords, API tokens) the compromised identity had read-access to, as the attacker may have stolen them.
- **Revert Unauthorized Changes:** Delete rogue EC2 instances, remove unauthorized IAM users or backdoor roles created by the attacker, and restore any modified security groups.
- **Strengthen Posture:**
  - Enforce MFA for all human users.
  - Implement Condition Keys in IAM policies (e.g., `aws:SourceIp`) to restrict where access keys can be used from (e.g., only allowing API calls from the corporate VPN IP space).
  - Move away from long-lived static access keys for workloads, relying instead on temporary credentials via IAM Roles (e.g., EC2 Instance Profiles, OIDC for GitHub Actions).
